## Correcciones necesarias al plan heredado

1. El spec y el prompt conservan referencias a Next 15 y a Contractors/Talleres como patrones. El repo usa Next 16.4.3; Contractors y Talleres no están en `main`. Seguir Realty y leer la documentación de Next instalada antes de tocar rutas.
2. El spec nombra `RetailLocation`; DEC-01 confirmó `Branch` + `RetailLocationSettings`. Las tablas, claves foráneas y el contrato web deben usar la decisión confirmada para evitar duplicar sucursales.
3. El spec ubica `RetailEmployee` en Fase 3, pero exige vendedor por venta en Fase 1. DEC-05 resolvió usar una identidad mínima de vendedor con PIN en Fase 1. Asistencia, nómina y control de personal completo quedan en Fase 3.
4. El contrato web vigente decía que una solicitud pública de apartado crea o vincula `Customer` por nombre y teléfono. Ese teléfono no está verificado. La propuesta corregida separa `Lead` de solicitud y `Customer` verificado, sin enlazar historiales por coincidencia de teléfono.
5. La contribución operativa necesita una comisión de pago real. Ni el spec ni el repo proporcionan una tarifa universal. Guardar comisión real por venta, o mostrar el indicador como pendiente cuando falte; no asumir comisión cero.
6. El código de prenda mostrado es un ejemplo. La regla final y el archivo real de GESEM siguen pendientes; no generar códigos productivos ni prometer una importación `.xlsx` sin revisar su formato.
7. La web pública está asignada a Claude y el núcleo a Codex en `DECISIONS.md`. Deben compartir un contrato versionado; la web no implementa transiciones de inventario por cuenta propia.
8. El PR #194 toma W-01 como opción A (publicar piezas `TIENDA` y `EN_LINEA`) y llama `requestHold` con `{ customer: { name, phone } }`, sin clave de idempotencia. Esta rama mantiene W-01 abierta hasta confirmación del negocio y propone `requester` + `requestKey` para el núcleo. Antes de conectar `source.ts`, adaptar la llamada y sus pruebas; el stub actual impide activar el flujo por accidente.
